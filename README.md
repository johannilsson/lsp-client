# lsp-client

A minimal CLI for querying a Language Server Protocol (LSP) server. Designed to be called by AI applications that need language intelligence (hover, definitions, references, diagnostics, completions) without bundling their own LSP client.

## Install

```sh
cargo install --path .
```

## Usage

```sh
lsp-client [OPTIONS] <COMMAND>

Commands:
  query         Run an LSP query against a file or workspace
  session       Manage the persistent LSP session daemon
  capabilities  List capabilities reported by the server
```

### Query subcommands

```
lsp-client query hover             <file> <line> <col>
lsp-client query definition        <file> <line> <col>
lsp-client query references        <file> <line> <col>
lsp-client query symbols           <file>
lsp-client query workspace-symbols <query>
lsp-client query diagnostics       <file> [--all]
lsp-client query completion        <file> <line> <col>
lsp-client query signature-help    <file> <line> <col>
lsp-client query code-action       <file> <line> <col>
lsp-client query rename            <file> <line> <col> <new-name>
lsp-client query semantic-tokens   <file>
lsp-client query inlay-hints       <file> [--start-line N] [--end-line N]
```

### Session subcommands

```
lsp-client session start      Start a persistent daemon for this workspace
lsp-client session status     Show daemon status (PID, socket, uptime)
lsp-client session stop       Stop the daemon
lsp-client session wait-ready Wait until the server has finished indexing
```

`session wait-ready` and `session start --wait` exit with 2 if the server is still busy when the timeout runs out, and with 3 if the project was not imported. The daemon keeps running in both cases.

kotlin-lsp reports a project that was not imported in two ways, and both give exit code 3 and a warning that says what happened:

- **The import failed**, for example `project import failed for /my/project/: Gradle sync failed`. Queries then return little or nothing. The server log has the details (`--verbose` prints its path).
- **The import was blocked**, because kotlin-lsp could not decide what to import: `no supported build system found in the project root`, or `more than one build tool found (gradle, maven)`. For the second case, choose one with `--build-tool gradle` (or `build_tool = "gradle"` in `.lsp-client.toml`). kotlin-lsp asks "Which build tool would you like to use?"; `--build-tool` answers by picking the button whose title contains that name, and the server remembers the answer for the workspace. Without it the question is dismissed. Only file-level queries (`symbols`, ...) work until the project is imported.

**Queries say so too.** A query still gets its answer, but when the daemon knows the project was not imported (or is still being imported) a warning is printed on stderr after it, because an empty answer then does not mean there is nothing to find. stdout, and `--json`, are unchanged. `lsp-client session status` shows the same under `import:`: `ok`, `running`, `problem` (with the reason), or `n/a` for servers that do not report project imports (rust-analyzer, for example). With `--json` it is an `import` object with `state` and `problems`. kotlin-lsp announces its own log file at startup. `session status` shows it as `server log:`, a failed-import warning names it, and `lsp-client session log` prints the end of it (`-n 100` for more lines). That is where the cause of a failure is, for example the Gradle build file and line that did not compile. The path is only known while the daemon runs; after `session stop`, `session log` has nothing to read.

**Changed a build file?** In testing, kotlin-lsp did not notice build-file edits while the daemon was running (editing the file on disk, sending `workspace/didChangeWatchedFiles`, or `didOpen` plus `didSave` of the file all left the old model in place; the server logs that it has no handler for `didChangeWatchedFiles`). Restart the daemon to import again: `lsp-client session stop`, then `lsp-client session start --wait`. The same goes for files generated by the build, such as `BuildConfig`.

kotlin-lsp stores its project model and index in a cache directory under the user's cache folder. To start from a clean import, point it at a directory of your own with `indexDir` (see below) and delete that directory.

Line and column numbers are 1-based.

## Daemon workflow (recommended)

Start a daemon once per workspace. Subsequent calls auto-connect.

```sh
# Start daemon
lsp-client session start --server <binary> --language-id <id> [--root /path/to/project]

# Query (auto-connects to daemon; --root defaults to cwd)
lsp-client query symbols src/Foo.kt
lsp-client query hover src/Foo.kt 42 10

# Check status
lsp-client session status

# Stop
lsp-client session stop
```

## Options

| Flag | Default | Description |
|---|---|---|
| `--root` | cwd | Project root directory |
| `--server` | — | Server binary to launch (required without a running daemon) |
| `--language-id` | — | Language ID for `didOpen` (required without a running daemon) |
| `--timeout` | — | Max time to wait for a response (e.g. `10s`, `2m`) |
| `--host` | `127.0.0.1` | Server host (TCP mode) |
| `--port` | `9999` | Server port (TCP mode) |
| `--no-server-stdio-flag` | — | Don't pass `--stdio` to the server process |
| `--build-tool` | — | Build tool to use when a project has more than one, e.g. `gradle` or `maven`. Only the `kotlin-lsp` profile uses it; other servers ignore it |
| `--json` | — | Emit `{"ok": true, "result": ...}` JSON |
| `--verbose` / `-v` | — | Debug logging to stderr |

## Configuration file

Instead of passing `--server`, `--language-id`, and other flags on every `session start`, you can place a `.lsp-client.toml` in your project root:

```toml
server      = "/path/to/kotlin-language-server"
language_id = "kotlin"
root        = "/path/to/your/project"   # defaults to cwd if omitted
timeout     = "30s"
no_server_stdio_flag = false
build_tool  = "gradle"                  # only needed when a project has both Gradle and Maven files

# Sent to the server as `initializationOptions` in `initialize`, exactly as written.
# Which keys exist depends on the server; see below for kotlin-lsp.
[initialization_options]
indexDir = "/path/to/index"
```

All fields are optional. `lsp-client` walks up from the current directory to find the nearest `.lsp-client.toml`, so placing it at the repo root covers all subdirectories.

With the file in place, starting a session is just:

```sh
lsp-client session start
```

## Server profiles

lsp-client works with any language server. What it does for every server stays at the protocol level. Behaviour that only one server needs (its own custom notifications, its own questions, how its output is tidied up) lives in a *profile* and runs only while that server is in use. Today there is one: `kotlin-lsp`, which reports project imports (`intellij/workspaceImportStatus` and `intellij/workspaceImportState`, undocumented messages), and which every other server never sees.

The profile is chosen after the server answers `initialize`: from the server's own `serverInfo.name` (kotlin-lsp calls itself "IntelliJ Language Server by JetBrains"), or by name with `--server-profile` / `server_profile` in `.lsp-client.toml`:

| Value | Meaning |
|---|---|
| `auto` (default) | match the server by what it calls itself; no match means `generic` |
| `generic` | turn every profile off |
| `kotlin-lsp` | use that profile even if the server does not identify itself |

`lsp-client session status` shows the profile in use. The code is in `src/servers/`, one module per server.

## Server-specific setup

### kotlin-lsp (Kotlin)

```sh
# macOS
brew install JetBrains/utils/kotlin-lsp
# Linux/Windows: download the standalone archive from
# https://github.com/Kotlin/kotlin-lsp/releases, unpack it and put bin/intellij-server
# on PATH as kotlin-lsp

# Recommended: daemon over stdio (starts once, serves all subsequent calls from a warm session).
# The first Gradle import of a project can take a minute or more: give --timeout room.
lsp-client --timeout 10m session start --server kotlin-lsp --language-id kotlin --root /my/project --wait
lsp-client query symbols src/Main.kt

# Direct TCP: attach to a server already running on port 9999 (e.g. started by IntelliJ)
lsp-client --tcp --language-id kotlin --root /my/project query symbols src/Main.kt

# Direct TCP with auto-start: spawn kotlin-lsp over TCP if none is listening
lsp-client --tcp --server kotlin-lsp --language-id kotlin --root /my/project query symbols src/Main.kt
```

**kotlin-lsp initialization options.** Put them in an `[initialization_options]` table in `.lsp-client.toml`; they reach the server unchanged as `initializationOptions`. kotlin-lsp does not document them. The names below come from the server's own option class and were not all tried:

| Key | What it is | Tried |
|---|---|---|
| `indexDir` | Directory for the project model and index. A fresh directory means a clean import. | yes: the server created it and imported into it |
| `buildTools` | Map of folder URI to build tool, e.g. `"file:///my/project/" = "gradle"` | no |
| `projects` | Projects to import in a workspace with several | no |
| `defaultSdk` | Path of the JDK to use | no |

```toml
[initialization_options]
indexDir = "/home/me/.cache/lsp-client/my-project"
```

### sourcekit-lsp (Swift)

sourcekit-lsp communicates over stdio and starts fresh per invocation, so the daemon is strongly recommended to avoid paying the startup cost on every call.

```sh
# sourcekit-lsp uses stdio by default — don't pass --stdio to the process
lsp-client session start --server sourcekit-lsp --no-server-stdio-flag --language-id swift --root /my/project
lsp-client query symbols Sources/App.swift
lsp-client --timeout 15s query hover Sources/App.swift 10 5
```

### rust-analyzer

```sh
lsp-client session start --server rust-analyzer --no-server-stdio-flag --language-id rust --root /my/project
lsp-client query diagnostics src/main.rs
```

## Testing

The integration tests run against a small fixture Rust project using rust-analyzer. Install rust-analyzer first if needed:

```sh
rustup component add rust-analyzer
```

Then run the tests serially (the daemon handles one connection at a time):

```sh
cargo test --test integration -- --test-threads=1
```

The first run starts a daemon for the fixture project and warms it up; subsequent runs reuse it. The daemon shuts itself down after 5 minutes of inactivity.

`tests/kotlin_lsp.rs` tests kotlin-lsp's project import handling (a folder without a build file, a folder with both Gradle and Maven files, and `--build-tool`) on tiny projects it creates in a temp directory. It needs `kotlin-lsp` on `PATH` and network access for Gradle, and is skipped with a note when kotlin-lsp is missing:

```sh
cargo test --test kotlin_lsp -- --nocapture --test-threads=1
```

## How it works

Query commands auto-detect a running daemon for the project root. If a daemon is running, the client connects to it over a Unix socket — no flags needed. The daemon starts the language server once over stdio, pays the startup and indexing cost once, then serves all subsequent calls from the warm session.

Pass `--tcp` to bypass the daemon entirely and connect directly to a TCP language server (e.g. kotlin-lsp on port 9999). This is useful when a server is already running — for example, started by an IDE — and you want to share it. Add `--server <binary>` to auto-start the server if none is listening.

## Known limitations

**Android projects (kotlin-lsp):** Android Gradle Plugin support in kotlin-lsp is experimental. Tested with kotlin-lsp 271.2085.0 on an AGP 9.5 / Gradle 9.8 app that uses a JVM-only `includeBuild`: once the Gradle sync succeeds, hover, definition, references, workspace symbols and diagnostics work, including across the included build and into library jars. Things to watch for:

- **The whole sync can fail on a variant you don't use** (tracked in [#21](https://github.com/johannilsson/lsp-client/issues/21)). kotlin-lsp builds a model for every variant, including `release` ([Kotlin/kotlin-lsp#291](https://github.com/Kotlin/kotlin-lsp/issues/291)). With AGP 9's Compose Preview support, the `release` variant fails because AGP disables its unit tests by default, and one failing task leaves the whole workspace without a model ([Kotlin/kotlin-lsp#283](https://github.com/Kotlin/kotlin-lsp/issues/283)). The project then gets no model at all: only `symbols` works, and diagnostics would come back silently empty. `session start --wait` and `session wait-ready` report this with exit code 3 and a warning. The server log has the cause (`Gradle sync failed`, and above it a line starting `Compose Preview failed for`); its path is printed at startup with `--verbose`. One workaround is to turn on host tests for `release` in `app/build.gradle.kts`:

  ```kotlin
  androidComponents {
      beforeVariants(selector().withBuildType("release")) {
          (it as com.android.build.api.variant.HasHostTestsBuilder)
              .hostTests[com.android.build.api.variant.HostTestBuilder.UNIT_TEST_TYPE]?.enable = true
      }
  }
  ```

- **`BuildConfig` (and other generated sources) are not generated by the server.** On a fresh clone they show up as `Unresolved reference` errors. Run `./gradlew :app:generateDebugBuildConfig` (or a build) *before* `session start`; files generated while the server runs are not picked up until a restart.
- Use AGP 9 / Gradle 9: older combinations can import with empty source roots ([#241](https://github.com/Kotlin/kotlin-lsp/issues/241)).

**Compose projects (kotlin-lsp):** `@Composable` function names are not reported as warnings. Compose names UI functions in UpperCase on purpose, and Android Studio does not warn about it, but kotlin-lsp reports `Function name 'Foo' should start with a lowercase letter` (inspection `FunctionName`) for every one. In text output, `query diagnostics` and `query context` leave out `FunctionName` diagnostics when the function is annotated `@Composable`. This also covers the qualified `@androidx.compose.runtime.Composable` and annotations spread over several lines; it does not match `@ComposableTarget` and similar. Naming warnings on other functions are still shown. Pass `--all` to `query diagnostics` to see everything the server reported. `--json` always returns the server's answer unfiltered.
